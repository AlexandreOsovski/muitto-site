What is MUITTO?

A minimalist test runner for TypeScript with zero runtime dependencies. describe, it, expect — the API you already know, with a matcher engine, mocks, fake timers and disk-backed snapshots built in. Curious how it works internally? That lives on the Guide page.

Install & usage

Install as a dev dependency and run straight from the CLI — there's no extra setup step.

Install

// with npm
npm install --save-dev @aleosovski/muitto

// or straight with npx, no install
npx muitto

Run the suite

npx muitto                       // runs everything
npx muitto --watch               // watches for changes
npx muitto --grep "sum"          // filters by name
npx muitto src/math.test.ts      // a specific file
Note

Config precedence is: CLI flags → .muittorc.json → "muitto" key in package.json → built-in defaults. Each layer only applies when the one before it doesn't define the value.

File discovery

With no arguments, MUITTO scans the project (ignoring node_modules, .git, dist, build, coverage, .next and .nuxt) and matches every path against the configured patterns.

// default patterns (customizable via pattern/testMatch)
"src/**/*.{test,spec}.ts"
"test/**/*.{test,spec}.ts"
"__tests__/**/*.ts"
"**/*.{test,spec}.ts"

Use --show-patterns to see exactly which patterns are active in your project.

Test functions

The building blocks for organizing and registering tests. describe/it only register — nothing runs until the runner drains the registry after the file finishes importing.

describe(name, fn)

describe(name: string, fn: () => void): void

Groups related tests into a named suite. Suites can nest freely. Aliases: suite, context (BDD style) — same function, different name.

import { describe, it, expect } from "muitto";

describe("Calculator", () => {
  describe("add", () => {
    it("adds two numbers", () => {
      expect(1 + 1).toBe(2);
    });
  });
});

it(name, fn) / test(name, fn)

it(name: string, fn: () => void | Promise<void>): void

Registers an individual test. fn can be synchronous or async — the runner awaits it either way. test is a plain alias for those who prefer Jest naming.

it("resolves asynchronously", async () => {
  const value = await fetchValue();
  expect(value).toBe("ok");
});

it.skip / describe.skip

Registers the test (or every test in the suite) but marks it to be reported as skipped instead of executed.

it.skip("not implemented yet", () => { /* ... */ });
describe.skip("legacy behavior", () => { /* every test inside is skipped */ });

it.only / describe.only

Exclusive mode: when at least one .only exists in a file, every test without .only in that file is skipped instead.

it.only("focus on this one while debugging", () => {
  expect(fn()).toBe(true);
});

it.todo(name)

it.todo(name: string): void

Registers a placeholder that always reports as skipped — a reminder to write the test later, without an empty it() body.

it.todo("handle expired tokens");

Parameterized tests

it.each<T>(table: T[])(name: string, fn: (...args) => void): void
it.each([
  [1, 2, 3],
  [4, 5, 9],
  [10, 20, 30],
])("sum $1 + $2 = $3", (a, b, expected) => {
  expect(sum(a, b)).toBe(expected);
});

// also works with objects: $property
it.each([{ name: "Ana", age: 30 }])(
  "$name should be an adult",
  ({ age }) => expect(age).toBeGreaterThanOrEqual(18)
);

Matchers

Wraps a value so matchers can be chained off it. Every matcher accepts negation via .not — expect(x).not.toBe(y).

Snapshots

toMatchSnapshot(options?: { name?: string }): void

Persisted to __snapshots__/<file>.snap, next to the test file — compared against previous runs and commits, not just within the same run.

import { expect } from "muitto";

it("user profile", () => {
  expect(getUserProfile()).toMatchSnapshot({ name: "user-profile" });
});
Tip

Changed on purpose? Run muitto --update-snapshots to rewrite it. On the first run, the snapshot is created automatically.

Asymmetric matchers

Useful inside toEqual/toHaveBeenCalledWith when only part of the value matters.

MatcherDescription
expect.any(Ctor)Matches any value that is an instance of Ctor
expect.anything()Matches anything except null/undefined
expect.arrayContaining(arr)Array that contains at least these items
expect.objectContaining(obj)Object that contains at least these keys/values
expect.stringContaining(str)String containing this substring
expect.stringMatching(pattern)String matching this regex
expect(user).toEqual({
  id: expect.any(Number),
  name: expect.stringContaining("Silva"),
  tags: expect.arrayContaining(["admin"]),
  meta: expect.objectContaining({ active: true }),
});

Need a custom matcher? expect.extend({ myMatcher(actual, ...args) { /* ... */ } }) registers it alongside the built-ins.

Mocks & spies

Create isolated mock functions or spy on existing methods without losing the original implementation.

fn(implementation?)

fn<T>(implementation?: T): MockFn<T>
import { fn } from "muitto";

const mockFn = fn();
mockFn.mockReturnValue(42);

expect(mockFn()).toBe(42);
expect(mockFn.mock.calls).toHaveLength(1);
expect(mockFn).toHaveBeenCalledWith();

spyOn(obj, methodName)

spyOn<T, K>(obj: T, methodName: K): SpyFn
import { spyOn } from "muitto";

const obj = { greet: (name) => `Hello ${name}` };
const spy = spyOn(obj, "greet");

obj.greet("World");
expect(spy).toHaveBeenCalledWith("World");

spy.mockRestore(); // restores the original implementation
Tip

Prefer toHaveBeenCalledTimes(n) over checking mock.calls.length directly — failures show the actual count in the error message.

mock.calls / mock.results / mock.instances

Every mock created with fn() or spyOn() exposes a .mock object tracking how it was used.

PropertyDescription
mock.callsArray of arguments for each call, in order
mock.resultsArray of { type: "return" | "throw", value } per call
mock.instancesThe this value each call was made with
const calc = fn((a, b) => a + b);
calc(2, 3);

expect(calc.mock.calls[0]).toEqual([2, 3]);
expect(calc.mock.results[0]).toEqual({ type: "return", value: 5 });

Controlling mock behavior

MethodDescription
mockImplementation(fn)Replaces the mock's underlying implementation
mockReturnValue(value)Always returns value
mockResolvedValue(value)Always returns a Promise resolved with value
mockRejectedValue(error)Always returns a Promise rejected with error
const fetchMock = fn();
fetchMock.mockResolvedValue({ data: "test" });

const result = await fetchMock("/api/data");
expect(result).toEqual({ data: "test" });

mockClear / mockReset / mockRestore

MethodDescription
mockClear()Clears calls/results/instances, keeps the current implementation
mockReset()Clears history and restores the implementation passed to fn()
mockRestore()Spies only — puts the original method back on the object
Tip

Call mockClear() in afterEach to keep call history from leaking between tests without losing a custom implementation.

Fake timers

useFakeTimers(): FakeTimersControl

Replaces setTimeout, setInterval and Date with controllable versions — the runner's own internal timeouts stay real and are unaffected.

import { useFakeTimers } from "muitto";

it("controls time", () => {
  const timers = useFakeTimers();
  let called = false;

  setTimeout(() => { called = true; }, 1000);
  timers.advanceTimersByTime(1000);

  expect(called).toBe(true);
  timers.restore();
});
Tip

Call timers.getTimerCount() right before restore() to catch a test that scheduled a timer it never expected to leave pending — a common source of flaky suites.

Timer control methods

Methods on the object useFakeTimers() returns.

MethodDescription
advanceTimersByTime(ms)Advances the clock by ms, running any callback whose time has come
advanceTimersToNextTimer()Jumps straight to the next pending timer and runs it; throws if none remain
runAllTimers()Repeatedly advances to the next timer until none remain
getTimerCount()Number of pending timers
restore()Restores the real setTimeout/setInterval/Date
Warning

Always call restore() — usually in afterEach. A test that leaves fake timers active can't disable the runner's own per-test timeout though: that one uses a real timer reference captured before any test file runs.

Retry

retry(fn: () => void | Promise<void>, options?: { times?: number; delay?: number }): Promise<void>

For tests that depend on unstable (flaky) asynchronous conditions. Defaults: times: 3, delay: 100ms.

import { retry } from "muitto";

it("retries on failure", async () => {
  let attempts = 0;

  await retry(async () => {
    attempts++;
    if (attempts < 3) throw new Error("not yet");
  }, { times: 5, delay: 100 });

  expect(attempts).toBe(3);
});

Lifecycle hooks

Scoped to the describe block they're called in. Aliases: setup/beforeEach, teardown/afterEach, before/beforeAll, after/afterAll.

HookDescription
beforeEach(fn)Runs before every test in the current suite
afterEach(fn)Runs after every test in the current suite
beforeAll(fn)Runs once, before the suite's first test
afterAll(fn)Runs once, after the suite's last test — errors here don't fail the suite
describe("Database", () => {
  beforeEach(async () => {
    await db.clear();
    await db.seed();
  });

  it("queries users", async () => {
    const users = await db.getUsers();
    expect(users).toHaveLength(1);
  });
});

Coming from Jest?

MUITTO's API was deliberately kept close to Jest's — describe, it, expect, and most matcher names are identical. Most Jest test files run with little to no changes.

What's the same

JestMUITTO
describe, it/testIdentical
it.skip, it.only, it.eachIdentical
beforeEach, afterEach, beforeAll, afterAllIdentical
toBe, toEqual, toContain, toThrow...Same names, same behavior
toMatchSnapshot()Same idea — persisted to __snapshots__/

What's different

JestMUITTO
jest.fn()fn() — named import, no global namespace
jest.spyOn(obj, method)spyOn(obj, method) — same signature, named import
jest.useFakeTimers()useFakeTimers() — returns a control object instead of mutating hidden global state
jest.mock('./module')Not supported — no module-level auto-mocking system, only fn()/spyOn()
toMatchObject(obj)Not implemented — use toEqual(expect.objectContaining(obj)) instead
Warning

The biggest gap is module mocking. If a suite relies heavily on jest.mock('./some-module') to swap out an entire module's exports, that pattern has no direct equivalent here — refactor to inject the dependency instead (pass a client/service in, mock it with fn()).

Testing Fastify apps

Fastify ships a built-in .inject() method that simulates HTTP requests without binding to a real port — it returns a plain promise, so it composes naturally with it.

import { describe, it, expect, beforeAll, afterAll } from "muitto";
import Fastify from "fastify";

function buildApp() {
  const app = Fastify();
  app.get("/health", async () => ({ status: "ok" }));
  app.post("/users", async (req, reply) => {
    if (!req.body.name) return reply.code(400).send({ error: "name required" });
    return reply.code(201).send({ id: 1, name: req.body.name });
  });
  return app;
}

describe("Fastify app", () => {
  let app;

  beforeAll(() => { app = buildApp(); });
  afterAll(async () => { await app.close(); });

  it("GET /health returns 200", async () => {
    const res = await app.inject({ method: "GET", url: "/health" });
    expect(res.statusCode).toBe(200);
    expect(res.json()).toEqual({ status: "ok" });
  });

  it("POST /users validates the body", async () => {
    const res = await app.inject({ method: "POST", url: "/users", payload: {} });
    expect(res.statusCode).toBe(400);
  });

  it("POST /users creates a user", async () => {
    const res = await app.inject({ method: "POST", url: "/users", payload: { name: "Ana" } });
    expect(res.statusCode).toBe(201);
    expect(res.json()).toEqual({ id: 1, name: "Ana" });
  });
});
Tip

Build the app fresh in beforeAll (or beforeEach if tests mutate shared state) rather than importing a singleton — it keeps test files isolated from each other, which matters since MUITTO runs files sequentially in the same process.

Testing Express apps

Express has no built-in request-injection helper, so the common pattern is to start the app on an ephemeral port and issue real HTTP requests against it with Node's built-in fetch — no extra dependency needed.

import { describe, it, expect, beforeAll, afterAll } from "muitto";
import express from "express";

function buildApp() {
  const app = express();
  app.use(express.json());
  app.get("/health", (req, res) => res.json({ status: "ok" }));
  app.post("/users", (req, res) => {
    if (!req.body.name) return res.status(400).json({ error: "name required" });
    res.status(201).json({ id: 1, name: req.body.name });
  });
  return app;
}

describe("Express app", () => {
  let server, baseUrl;

  beforeAll(async () => {
    const app = buildApp();
    server = app.listen(0); // port 0 = ephemeral, avoids clashes
    await new Promise((resolve) => server.once("listening", resolve));
    baseUrl = `http://localhost:${server.address().port}`;
  });

  afterAll(() => new Promise((resolve) => server.close(resolve)));

  it("GET /health returns 200", async () => {
    const res = await fetch(`${baseUrl}/health`);
    expect(res.status).toBe(200);
    expect(await res.json()).toEqual({ status: "ok" });
  });

  it("POST /users creates a user", async () => {
    const res = await fetch(`${baseUrl}/users`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ name: "Ana" }),
    });
    expect(res.status).toBe(201);
    expect(await res.json()).toEqual({ id: 1, name: "Ana" });
  });
});
Note

Already using supertest elsewhere? It works fine here too — it's just a request-assertion library, not tied to any particular test runner. The fetch-based approach above just avoids adding a dependency for it.

CLI

muitto [options] [files...]

FlagDescription
--watch, -wRuns in watch mode, observing the whole project
--grep <pattern>Runs only tests/suites whose name contains the pattern
--reporter <name>default, verbose, dot, json, junit
--output, -o <file>Writes the report to a file (json/junit reporters)
--update-snapshotsRewrites diverging snapshots instead of failing
--timeout, -t <ms>Timeout per test (default: 5000ms)
--bailStops execution on the first failure
--show-patternsLists the currently configured discovery patterns
--help, -h / --version, -vHelp and version
Warning

--coverage signals intent, but coverage instrumentation isn't implemented yet — the flag currently just prints a warning.

Config file

Optional. Use .muittorc.json at the project root, or the "muitto" key in package.json.

{
  "pattern": ["src/**/*.spec.ts"],
  "testPathIgnorePatterns": ["/fixtures/"],
  "timeout": 10000,
  "reporter": "verbose",
  "bail": false,
  "updateSnapshots": false
}

Patterns support **, *, ? and {a,b} alternation — the same format used by the built-in patterns.

Reporters

defaultFull, colored interface, built for the local terminal
verboseShows every test individually as it runs

muitto --reporter junit --output ./junit.xml
