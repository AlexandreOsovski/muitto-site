The philosophy

Built without dependencies. Not even this site.

A minimalist test runner for TypeScript — and the thinking behind it.

What is MUITTO?

MUITTO is a minimalist, zero-dependency test runner for TypeScript. No config files to fight, no plugins to wire up — install it, write a describe/it block, and run. It's fast, lightweight, and built to be read — not just executed.

Why the name?

"MUITTO" comes from muito, Portuguese for "a lot" or "very" — a Brazilian expression that captures the whole philosophy in one word. Deliver everything you need for testing, with nothing you don't. Maximum capability, minimum overhead. Simple. Direct. Powerful.

How it works under the hood

There's no bundler, no plugin system, and — outside of tsx for transpiling TypeScript in dev — no runtime dependencies at all. When you run muitto, it loads config from .muittorc.json / package.json, then walks your project comparing every file path against the configured glob patterns: a small hand-written matcher supporting **, *, ? and {a,b}, no external glob library involved.

Each matched file is imported with a cache-busting query string (?t=timestamp-random), so watch mode always re-reads fresh code instead of a stale cached module. Calling describe/it doesn't run anything yet — it just registers the test into a shared registry, keyed via Symbol.for('muitto.registry') on globalThis so it stays the same array no matter how the module gets resolved. Once the file finishes importing, the runner drains that registry, runs each test's hooks and timeout in sequence, and reports the result — before moving to the next file.

Files run one after another, not in parallel — it keeps output deterministic and avoids the complexity of merging results across processes. Every test gets its own timeout, guarded by a real setTimeout reference captured before any test file runs, so a test that calls useFakeTimers() and forgets to restore it can't accidentally disable the runner's own timeout.

Reporters are a small observer interface — onStart, onFileStart, onTestEnd, onEnd — completely decoupled from execution, which is why default, dot, verbose, json and junit all run through the exact same code path. Snapshots follow the same boring-on-purpose approach: they're written to a plain .snap JSON file under __snapshots__/, next to the test file, and compared on every future run — including in CI.

Installation & usage

Install as a dev dependency and run straight from the CLI — there's no extra setup step.

Install

// with npm
npm install --save-dev @aleosovski/muitto

// or straight with npx, no install
npx muitto

Run the suite

npx muitto                       // runs everything
npx muitto --watch               // watches for changes
npx muitto --grep "sum"          // filters by name
npx muitto src/math.test.ts      // a specific file

Config precedence is: CLI flags → .muittorc.json → "muitto" key in package.json → built-in defaults. Full details on the API reference.

File discovery

With no arguments, MUITTO scans the project (ignoring node_modules, .git, dist, build, coverage, .next and .nuxt) and matches every path against the configured patterns.

// default patterns (customizable via pattern/testMatch)
"src/**/*.{test,spec}.ts"
"test/**/*.{test,spec}.ts"
"__tests__/**/*.ts"
"**/*.{test,spec}.ts"

Use --show-patterns to see exactly which patterns are active in your project.

Writing tests

The same describe/it/expect shape you already know. Suites can nest, tests can be async, and nothing runs until the runner drains the file's registry.

A basic suite

import { describe, it, expect } from "muitto";

describe("Calculator", () => {
  it("adds two numbers", () => {
    expect(1 + 1).toBe(2);
  });

  it("resolves asynchronously", async () => {
    const value = await fetchValue();
    expect(value).toBe("ok");
  });
});

Skipping and focusing tests

.skip reports as skipped instead of running. .only is exclusive: once one exists in a file, everything else in that file is skipped.

it.skip("not implemented yet", () => { /* ... */ });

it.only("focus on this one while debugging", () => {
  expect(fn()).toBe(true);
});

Parameterized tests

it.each([
  [1, 2, 3],
  [4, 5, 9],
  [10, 20, 30],
])("sum $1 + $2 = $3", (a, b, expected) => {
  expect(sum(a, b)).toBe(expected);
});

Mocks & spies

Create isolated mock functions with fn(), or spy on an existing method with spyOn() without losing its original implementation.

import { fn, spyOn } from "muitto";

const mockFn = fn();
mockFn.mockReturnValue(42);
expect(mockFn()).toBe(42);
expect(mockFn).toHaveBeenCalledWith();

const obj = { greet: (name) => `Hello ${name}` };
const spy = spyOn(obj, "greet");
obj.greet("World");
expect(spy).toHaveBeenCalledWith("World");
spy.mockRestore(); // restores the original implementation

Every mock tracks .mock.calls and .mock.results, and can be reset with mockClear()/mockReset() — see the full API reference.

Fake timers

Replace setTimeout, setInterval and Date with controllable versions — the runner's own internal timeouts stay real.

import { useFakeTimers } from "muitto";

it("controls time", () => {
  const timers = useFakeTimers();
  let called = false;

  setTimeout(() => { called = true; }, 1000);
  timers.advanceTimersByTime(1000);

  expect(called).toBe(true);
  timers.restore();
});

Snapshots

Persisted to __snapshots__/<file>.snap, next to the test file — compared against previous runs and commits, not just within the same run.

it("user profile", () => {
  expect(getUserProfile()).toMatchSnapshot({ name: "user-profile" });
});

Changed on purpose? Run muitto --update-snapshots to rewrite it. On the first run, the snapshot is created automatically.

Retry

For tests that depend on unstable, flaky asynchronous conditions. Defaults: times: 3, delay: 100ms.

import { retry } from "muitto";

it("retries on failure", async () => {
  let attempts = 0;

  await retry(async () => {
    attempts++;
    if (attempts < 3) throw new Error("not yet");
  }, { times: 5, delay: 100 });

  expect(attempts).toBe(3);
});
